Here's the case study, anonymized. Project Sentinel is a codename. It's an agent that helps a security review team at a large tech company triage third-party risk. The key design choice: formulas handle anything that can be scored deterministically; the agent only does the interpretive parts, like spotting answers that contradict each other, judging how mature a process is, and writing the narrative. MCP servers connect it to the team's data tools. Humans review the results, and their feedback improves the next run. It runs nightly. Hold this shape: the demo later works the same way.

The shift

From chatbots to agents

Chatbot answers

  • You ask, it replies
  • Knows what it was trained on
  • You do the work
→

Agent acts

  • You give it a goal
  • It calls tools to look things up and do things
  • It loops until the job is done, or asks you
A chatbot answers. An agent acts. The difference is tools and a loop: the model can decide to call a function, see the result, and keep going until the goal is met.

Definition

What is an agent?

Modeldecides what to do next
+
Toolsfunctions it can call
+
Loopcall, observe, repeat
+
Contextgoal, history, data

= an agent

My working definition: model plus tools plus a loop plus context. The model picks the next step, tools let it act, the loop lets it react to results, and context is everything it knows about the task. Remove any one and it stops being an agent.

How it works

The tool-calling loop

1Goal + contextsent to the model
2Model decidesanswer, or call a tool
3Host runs the toolyour code, your rules
4Result goes backinto the context
repeat until done

The model never runs code. It asks.

Walk the loop one step at a time. Key point on step 3: the model only produces a request to call a tool with some arguments. Your program decides whether to run it. That is where safety and control live. Then the result goes back into the conversation and the model decides again.

The problem

Every app wired to every tool

N × Mcustom integrations: every AI app builds its own connector to every tool
N + Mwith one shared protocol: build a tool once, use it from any app
Before a standard, every AI app had to write its own connector for every tool or data source. That is N times M pieces of glue code. A shared protocol turns it into N plus M: each app speaks the protocol once, each tool speaks it once.

Model Context Protocol

MCP: an open protocol

A standard way for AI apps to connect to tools and data. Introduced by Anthropic in November 2024.

MCP, the Model Context Protocol, is an open protocol introduced by Anthropic in November 2024. Three roles: the host is the app you use. Inside it, a client holds one connection to one server. A server exposes capabilities. You write a server once and any MCP host can use it.

What travels over MCP

The primitives

Servers offer

Toolsfunctions the model can call
Resourcesdata the app can read
Promptsreusable templates

Clients offer

Samplinga server asks the host's model for a completion
Rootswhich files and folders a server may work in
Elicitationa server asks the user for more input
Servers offer three things: tools the model can call, resources the app can read, and prompts, which are reusable templates. Clients offer things back: sampling lets a server ask for a model completion through the host, roots tell a server where it may work, and elicitation lets a server ask the user a question. Today's demo uses tools and one resource.

Under the hood

It's just JSON-RPC 2.0

→ request

{ "jsonrpc": "2.0", "id": 1,
  "method": "tools/list" }

← response (trimmed)

{ "tools": [{
    "name": "size_market",
    "title": "Size the market",
    "inputSchema": { "type": "object",
      "properties": {
        "customer_count": { "type": "integer" },
        "annual_price_usd": { "type": "number" }
      } } }, … ] }

→ request

{ "jsonrpc": "2.0", "id": 2,
  "method": "tools/call",
  "params": { "name": "size_market",
    "arguments": {
      "segment": "US college students",
      "customer_count": 1000,
      "annual_price_usd": 60,
      "serviceable_share": 0.2,
      "obtainable_share": 0.05 } } }

← response (trimmed)

{ "structuredContent": {
    "tam_usd": 60000, "sam_usd": 12000,
    "som_usd": 600 } }
No magic. These are real messages from the server in today's demo, trimmed. tools/list returns each tool's name, description and a JSON Schema for its input. tools/call sends arguments and gets a structured result back. The numbers here are toy inputs to show the format, not real market data.

Transports and trust

Where it runs, who it trusts

stdio

Server runs as a local child process. No network port at all.

Streamable HTTP

Server runs remotely over HTTP. Needs real authentication and HTTPS.

  • Local only: our demo listens on 127.0.0.1
  • API keys live in environment variables, never in code or the browser
  • Least privilege: each tool does one narrow thing
  • Tool output is data, not instructions
Two transports. stdio: the host starts the server as a child process and talks over standard input and output, so nothing listens on the network. Streamable HTTP: for remote servers, which then need proper authentication. The trust rules I follow every day are on screen. The last one matters most: anything a tool returns could contain text that tries to steer the model, so treat it as data.

Recap

What just happened

  1. The agent read a resource: the pitch rubric
  2. It made four tool calls, each with JSON in and JSON out
  3. It wrote a verdict from the results

The model never saw our code. It saw names, descriptions and schemas.

Same loop as before, now concrete. One resource read, four tool calls, one final answer. The model only knew what the MCP server told it: tool names, descriptions and input schemas. That is why good tool design is most of the job.

Lessons from the job

What actually makes agents work

Evals

Keep a test set of real cases. Without it you're guessing.

Guardrails

Formulas for math, the model for judgment. Validate every tool input.

Humans in the loop

Show the reasons, not just the score, so people can check the work.

Cost and latency

Every loop step is a model call. Fewer, better tools win.

Four lessons. Evals: the most important habit; keep real examples and rerun them on every change. Guardrails: on Project Sentinel, anything that can be computed is a formula, not a model call, and every tool input has a schema. Humans in the loop: reviewers check the results, and their feedback shapes the next run. Cost and latency: each step of the loop costs time and money, so design tools that do a meaningful chunk of work.
